# Cross-product integration design

Use parent R1–R10 as the sole umbrella requirements. Maintain an evidence matrix per language/product/backend and item. Each report identifies exact content/runtime hashes, device/build identity, assertion and outcome. Distinguish missing, unsupported, failed and passed; do not collapse any into generic success.

Shared changes are coordinated by file responsibility. Proposed diagnostics and debugger APIs are optional profile hooks, enabling staged adapters while preserving old apps. Content authors use their own repository sources or staged slices; the one shared integrator validates unknown edits/digests and applies only authorized slices. Existing contentRepositoryFactory can isolate product curricula where explicitly agreed and tested, but must not hide unresolved baseline content.

Language highlighting is validated with actual token spans for every advertised language and important aliases; visual plain text is not a successful syntax-highlighting test. Learning filters operate on visible catalog languages. Workspace persistence migrates old single-project sessions without data loss; owner identity follows open file tabs and tools.

Integration reviews check real routes/widgets as well as data models. Wave underlines and Problems navigation require source-range and unsaved-buffer tests. Actual breakpoint execution and port introspection remain capability-backed. All product tests run against the final shared revision, not earlier independently passing cores.

Publication is a sequence of audited conventional commits across separate repos. Shared-core SHA and product SHAs are recorded together. A failed push is reported without force or rewriting unrelated history; a build without target execution does not satisfy OHOS acceptance.
